# arXiv 路由与 Semantic Scholar 限流修复

## arXiv：修复的是错误的巡检路由

此前 `tools/engine_health.py` 固定使用直连，忽略了本机已经配置的 HTTP(S) 网络路由。
相同官方 `export.arxiv.org` 接口的有限对照显示：直连约 13 秒超时；已有路由下按 ID 和
固定关键词请求分别约 1.11、1.48 秒返回正常 Atom。没有更换 IP、切换镜像或轮换代理。

实际 `search_arxiv` SDK 经真实工作进程验证返回 1 条记录，`source=arxiv`，约 1.77 秒。
2026-10-15 **17:15 北京时间**的修正后巡检也返回 `healthy`、HTTP 200、1 条记录，约 0.42 秒。
这些是本次有限观察，不能保证持续可用，也不表示直连已恢复。

巡检现在默认 `--network configured`，只使用已配置且没有用户名/密码的 HTTP(S) 路由；
拒绝远程明文 HTTP 代理、凭据、未知代理协议，不输出地址。
无代理配置时仍直接访问。保留显式 `--network direct`，报告标注网络模式，便于区分路径。
不会在直连失败后自动遍历其他路由，仍然每个所选引擎最多一次请求。
客户端分页间隔从 1 秒修正为 3 秒，SDK 重试上限降至 1，父进程 25 秒上限保持。
这是客户端内的间隔，不是所有用户进程或其他程序的全局限速器；避免并行启动独立 arXiv 查询。

```console
python tools/engine_health.py --live --engine arxiv
python tools/engine_health.py --live --engine arxiv --network direct
```

## Semantic Scholar：减少无效重试，保留共享限流事实

无密钥调用使用共享额度。此次真实搜索与修正后巡检仍返回 429，因此不宣布远端限流已消除。
自动创建账号、使用新密钥或付费套餐都没有执行，也不需要为本轮修复这样做。

- 匿名请求遇到 429 后立即停止当前请求的重试，释放执行时间，让其他已选引擎继续。
- 已配置 `S2_API_KEY` 时才允许有限退避；读取 `Retry-After` 的秒数或 HTTP 日期，等待不得短于
  服务器建议。建议时间超出本次预算时不提前重试，返回当前失败。
- 本次请求/等待总预算 20 秒，每次 HTTP 等待最多 8 秒，受原有父进程截止时间进一步约束。
- 现有 HTTP 二元返回值保持兼容，只通过可选输出字典传递 `Retry-After`，不复制 Cookie 等头部。
- 不会偷偷换为另一来源并标作 S2。需要继续检索时，可显式选择已有来源：

```console
pa search "your query" --engine crossref,openalex
```

这没有跨进程全局额度协调，也不保证密钥调用永不出现 429。当前只修复单次操作中的重复请求
与截止时间行为。连续新开进程仍可能触发服务端限流；不要高频重试。

## 验证和维护

三轮离线能力门，每轮 **49 项测试、54 个子测试**通过，新增 8 项恢复检查覆盖配置路由、
凭据/远程明文代理拒绝、匿名 429 单次调用、带密钥的服务器退避、长冷却期停止、
HTTP 日期解析、错误响应关闭及 SDK 间隔。新增测试不使用真实密钥或外部请求。
全部十项当前提交 CI 仍是合并条件；在线观察不是强制 CI。

每周维护使用默认配置路由，同时保存网络模式。旧的直连 arXiv 超时基线需以此次有日期的
配置路由观察更新，保留 S2 限流，不把未选的其他引擎登记为本次通过。
没有论文正文、语料收集、人工标注、模型评测、新依赖或发布版本。

来源：[arXiv 官方 API 条款](https://info.arxiv.org/help/api/tou.html)要求至少 3 秒间隔、单连接；
[Semantic Scholar 官方教程](https://webflow.semanticscholar.org/product/api/tutorial)
解释匿名共享额度与 429 的含义。客户端行为另经本机已安装的 arxiv 4.0.1 源码核对。
